# 个人网站目标与需求基线

## 项目使命

将现有 AstroPaper 项目逐步完善为一个以中文个人博客和学习笔记为核心的 GitHub
Pages 静态网站。网站应保持轻量、可访问、可搜索、易发布、低维护，并确保任何改进
都不会破坏用户当前未提交工作。

## 已确认的项目事实

- 仓库：`araragi-koyomin/araragi-koyomin.github.io`
- 本地目录：`E:\website1`
- 源码分支：`main`
- 发布分支：当前为 `gh-pages`
- 框架：Astro 5.12.0、AstroPaper 5.x、Tailwind CSS 4、TypeScript
- 内容来源：`src/data/blog` Markdown 内容集合
- 当前线上版本已于 2026-08-30 发布为“私立直江津高校”，包含中文站点身份、四个主栏目
  和当前公开文章。
- 工作区中的用户修改始终必须完整保留；发布前应明确检查暂存范围。

## 已确认的管理需求

- 正式完善网站前，先建立项目管理与文档治理规则。
- 根目录必须存在 `AGENTS.md`。
- 新产生的开发文档除 `AGENTS.md` 外全部放入 `docs/`，不得作为网站内容发布。
- 所有 `docs/**/*.md` 必须包含 YAML frontmatter。
- 文档按热层、温层、冷层管理；归档不是删除。
- `docs/BACKLOG.md` 是唯一热层索引，只保留活跃事项。
- 新需求、新功能开发、状态变化、阻塞和完成都必须同步更新 BACKLOG。
- 如果需求存在会影响范围的歧义，或方案对个人博客明显过度复杂，必须立即向用户提出。
- 所有阶段更新和最终汇报都必须提供足够的背景、判断依据、影响范围、当前状态和
  下一步，不能只给状态词或未经解释的编号。
- 专业术语、英文缩写和事项编号第一次出现时必须使用常见中文解释其含义、项目行为、
  重要性和失败后果；用户没有理解时，应暂停依赖该理解的重大决定并重新解释。
- 需要用户选择方案时，必须逐项说明修改范围、不修改范围、优缺点、风险、工作量和
  推荐理由；审查结论必须转换为用户能够实际验证的页面、请求或结果。

## 改进目标

长期内容范围包括：

- 学习记录：秋招面试经历、人工智能智能体知识、LeetCode 解题思路及其他学习心得。
- 游戏记录：《蔚蓝》模组地图体验与汇总、《我的世界》模组和整合包体验，以及其他
  Steam 游戏分享。
- WOTA艺记录：个人作品、喜欢的技连或企划作品、副歌技汇总。
- 动漫记录：观看感受、分享和未来可能的作品汇总。

这里的“人工智能智能体”对应用户所说的 Agent，是能围绕目标规划步骤并调用工具的
程序；“模组”对应 Mod，是玩家或社区制作的游戏扩展内容。具体内容结构、导航和待确认
问题见 [CONTENT-ARCHITECTURE.md](CONTENT-ARCHITECTURE.md)。

当前内容体系采用“一个主分类加多个标签”、小型全站导航和英文小写网址。学习内容主要
服务于作者长期回顾；游戏、WOTA艺和动漫内容主要面向公开分享。以上是允许随实际前端
展示继续调整的实施基线，不是不可修改的永久规则。

### G-01：可靠基线

当前工作树应能在明确的 Node/pnpm 环境下完成类型检查、lint、格式检查和生产构建，
且不依赖偶然的本地状态。

### G-02：真实个人内容

公开文章、标签、About、README 和静态资源只保留用户确认的内容，不把 AstroPaper
模板教程误当成个人文章发布。

### G-03：一致的站点身份

站点标题、作者、公开 profile、仓库编辑链接、描述、favicon、OG 图片和版权信息必须
指向同一套已确认身份。

### G-04：统一的中文体验

导航、页面标题、日期、搜索、归档、分页、分享、返回按钮、错误页、辅助文本和 HTML
语言属性应遵循已确认的语言策略。

### G-05：笔记写作能力

Markdown 应稳定支持目录、代码高亮、图片、行内/块级数学公式、标签、草稿、定时发布
和可预测 URL。

### G-06：可发现性与可访问性

主要页面应具备正确的 canonical、Open Graph、结构化数据、RSS、sitemap、robots，
并可通过键盘和常见屏幕尺寸正常使用。

栏目浏览还应支持同一内容的多条发现路径：主分类、主题标签、内容类型、发布时间和
全文搜索。静态筛选状态应保存在网址中，便于收藏、分享和从外部链接直接进入。

### G-07：可重复发布

CI 与部署文档应准确反映 `main` 到 GitHub Pages 的真实链路；只有用户明确授权时才能
执行部署。

### G-08：低摩擦文章编写

VS Code 写作流程应能通过结构化选择和可编辑模板减少重复 Frontmatter 操作，并提供
标签、子主题、图片、内部链接、常用 Markdown 结构、修改时间和真实页面预览辅助。
工具不得改变 Markdown 内容源、绑定不可逆专有格式，或自动执行 Git 提交和发布。

## 非目标与复杂度边界

在用户另行确认前，不引入：

- 服务端运行时、数据库或用户账号系统
- 线上 CMS、评论后端、分析平台或付费 SaaS；本地 VS Code 内容辅助扩展允许先行试用
- 与个人博客规模不匹配的大型状态管理或设计系统
- 自动提交、自动推送或未经确认的生产部署
- 与已确认内容目标无关的全面重写

若未来需求确实需要这些能力，必须先比较静态或更简单的替代方案。

## 总体验收标准

- 获准的 lint、格式、类型检查和生产构建通过。
- 首页、博客、文章、标签、归档、搜索、RSS、sitemap、robots、404 和 OG 路由可用。
- 模板身份、错误仓库链接、占位账号和未确认模板文章不再公开。
- 中文内容、公式、代码块、图片和移动端布局显示正确。
- README、配置、CI、部署分支和线上结果一致。
- 每项工作均按三层记忆规则更新文档，BACKLOG 不包含已完成事项。

## 已确认的产品决定

### D-001：公开内容

公开站点只保留用户的个人文章和笔记。AstroPaper 教程、示例和 release 文章不再作为
公开博客内容，但 AstroPaper 继续作为网站框架使用。

### D-002：语言

网站界面全面使用简体中文。必要的英文技术术语可以保留，但第一次出现时应提供中文
解释，不能形成未经说明的中英文混用。

### D-003：About 页面

保留并重写 About 页面，用于介绍作者和网站用途。已批准的正文为：

> 你好，我是往目琛。这里是“私立直江津高校”的图书馆，用来整理和分享我的学习、
> 游戏、生活记录以及个人文章。你可以通过 GitHub 查看我的公开项目。

实现时将 `GitHub` 链接到 `https://github.com/araragi-koyomin`，不得擅自补充真实姓名、
教育经历、联系方式或其他未确认的个人信息。

### D-004：作者身份

公开显示名称统一为“往目琛”，profile 指向
`https://github.com/araragi-koyomin`。文章作者、版权信息、结构化数据和站内相关链接应
保持一致。

### D-005：站点标题

正式站点标题使用“私立直江津高校”，首页栏目标题使用“图书馆”。实现时应避免让
页面结构或文案暗示这是现实学校的官方网站。

### D-006：部署

继续使用 GitHub Actions 构建并将产物写入 `gh-pages`，但发布流程改为用户手动触发。
推送 `main` 不应自动发布。任何实际部署仍需用户在当次任务中明确授权。
工作流使用 GitHub 自动签发且仅对本次运行有效的 `GITHUB_TOKEN`，不再依赖需要人工
续期的个人访问令牌。

### D-007：内容架构与个人评价

内容采用一个主分类加多个标签、小型全站导航和英文小写网址。WOTA艺保持“我的作品”、
“我喜欢的作品”和“副歌技汇总”三个并列入口，企划和技连作为作品呈现形式。
WOTA艺文章必须明确填写三个分区之一；三类上方的总结是栏目固定文字，不作为文章发布，
当前保持空白并在用户填写前隐藏。

游戏和动漫内容同时保留十分制浮点评分与十分制浮点推荐度：评分衡量作者对作品或体验
本身综合质量的评价；推荐度衡量作者愿意向目标读者推荐它的程度，并考虑受众匹配、
入门门槛等因素。定性推荐档位从推荐度自动换算，具体档位和阈值在前端设计时确定。
完整规则见 [CONTENT-ARCHITECTURE.md](CONTENT-ARCHITECTURE.md)。

### D-008：文章编写工具试用

先试用 Front Matter CMS 的 VS Code 本地扩展，实际体验后再决定是否保留。新文章目录
暂按 `src/data/blog/<主栏目>/<子主题>/` 组织；`slug` 自动生成策略暂缓。标签搜索、
子主题注册表、图片导入、内部链接选择、代码块/数学公式/来源链接快捷插入，以及旧文章
`modDatetime` 更新建议是最终方案的必做能力。若现成扩展不足，保留开发本地 VSIX
专用扩展的备选方案。详细范围见 [POST-AUTHORING.md](POST-AUTHORING.md)。
