# 内容架构与长期写作需求

## 文档状态

信息架构是内容如何分类、命名、互相关联、被导航和被搜索的整体规则。本文件记录当前
采用的轻量方案，不代表不可变的最终设计。用户已说明，后续可以根据实际前端展示方式
继续调整和细化；调整时必须同步更新本文和 `docs/BACKLOG.md`。

分类、栏目关系和评价字段的语义已经确认，可以作为后续页面和文章模板设计的起点。
定性推荐档位的名称和换算阈值留到实际前端展示设计时确定，它是展示细节，不再阻塞
内容模型。

## 内容范围与主要受众

```text
内容
├── 学习
│   ├── 秋招面试经历
│   ├── 人工智能智能体学习
│   ├── LeetCode 解题思路
│   └── 其他学习心得
├── 游戏
│   ├── 蔚蓝（Celeste）
│   │   ├── 模组地图推图记录与感受
│   │   └── 已游玩地图汇总与总体评价
│   ├── 我的世界（Minecraft）
│   │   ├── 模组玩法记录
│   │   └── 整合包体验与汇总
│   └── 其他 Steam 游戏记录
├── WOTA艺
│   ├── 我的作品
│   ├── 我喜欢的作品
│   └── 副歌技汇总
└── 动漫
    └── 按季度、剧场版或独立作品记录观看感受与分享
```

- 学习内容主要用于作者自己整理和回顾，可以更偏向高密度笔记，但仍应保留标题、日期、
  主分类、标签和来源等基本信息，确保以后能找到和理解。
- 游戏、WOTA艺和动漫内容具有明确分享目的。正文应让不掌握作者个人上下文的读者也能
  理解，并清楚标注作品来源、适用对象、剧透和主观评价。

人工智能智能体对应用户所说的 Agent，是能根据目标规划步骤、调用工具并执行任务的
程序。模组对应 Mod，是玩家或社区制作的游戏扩展内容。WOTA艺术语无需在公开博客中
额外设置科普说明；项目文档中的解释只服务于内部分类和开发沟通。

## 当前采用的轻量内容模型

“元数据”是写在文章开头、用于分类和生成列表的结构化信息，例如标题、日期和标签。
当前采用“一个主分类加多个标签”的模型：

- 主分类：`学习`、`游戏`、`WOTA艺`、`动漫` 四选一。
- 子主题：例如 `秋招面试`、`人工智能智能体`、`LeetCode`、`Celeste`、`Minecraft`。
- 标签：记录可跨分类复用的主题、技术、作品名、模组名或内容特征。
- 内容类型：区分普通记录、推图记录、解题记录、作品分享、评价和汇总。
- 状态：继续使用草稿与发布日期；需要时增加游玩、观看或完成状态。

一篇文章不同时归入多个主分类，以避免重复列表、网址不稳定和读者不知道应该从哪个
栏目进入。跨栏目关系通过标签和相关文章表达。例如一篇分析《我的世界》自动化模组的
学习文章，可以把主分类设为“游戏”，再使用“自动化”和“学习笔记”标签。

## 共用文章字段

第一阶段已经把以下字段加入 Astro 内容集合，并由统一组件负责列表和正文展示。模板
文章已经清理，现有个人文章也已完成迁移，因此 `category` 和 `contentType` 现在是必填
字段；新文章漏填时会在 Astro 内容检查阶段直接报错，避免文章从栏目页中静默消失。

| 字段 | 用途 | 当前决定 |
|---|---|---|
| `category` | 决定文章所属的主要栏目 | 必填，四个主分类之一 |
| `subcategory` | 表示栏目内的稳定子主题 | 选填，例如 Celeste |
| `wotaSection` | 决定 WOTA艺文章进入哪个固定分区 | WOTA艺文章必填，其他栏目禁止填写 |
| `contentType` | 区分笔记、体验、解题、评价、汇总等页面用途 | 必填，词表由代码统一维护 |
| `tags` | 支持跨主题查找和关联 | 保留现有能力 |
| `status` | 游玩、观看、解题或整理进度 | 按栏目选填 |
| `rating` | 作者对作品或体验本身综合质量的个人评价 | 十分制，允许小数 |
| `recommendationScore` | 作者愿意向目标读者推荐它的程度 | 十分制，允许小数，考虑受众匹配和入门门槛等因素 |
| `spoiler` | 提醒文章是否包含剧透 | 游戏和动漫使用布尔值 |
| `sourceLinks` | 指向题目、地图、整合包或作品来源 | 选填；每项保存显示名称与网址 |
| `celesteVideoUrl` | 指向该 Celeste 地图游玩视频的 Bilibili 网址 | Celeste 地图文章选填；只在文章详情页显示 |
| `heroImage` | 在文章元数据与正文之间显示独立封面图 | 选填，只使用项目媒体库中的本地图片 |
| `heroImageAlt` | 用文字说明封面图表达的内容 | 公开文章设置封面时必填 |
| `heroImageCaption` | 在封面图下方补充来源或简短说明 | 选填；未设置封面时不得单独填写 |
| `ogImage` | 控制社交平台链接预览图片 | 与正文封面分离，不自动显示在文章内 |

这里的“浮点”表示可以记录带小数的数值，例如 `8.5`。`rating` 与
`recommendationScore` 都已经限制在零到十分之间。定性推荐档位不保存到文章；以后确认
名称和阈值后由推荐度自动计算，避免数值与文字互相矛盾。字段也不应一次全部强制填写，
只把确实用于导航、汇总或搜索的字段设为必填，避免短记录变成复杂表单。

文章封面使用独立字段而不复用 `ogImage`。这样作者可以让正文封面采用适合阅读的图片，
同时继续让社交分享图服务于链接预览；没有封面的文章不生成空白区域。封面统一在标题、
日期和栏目元数据之后显示，桌面与手机均使用 16:9 容器裁切，完整图片仍可在正文中按普通
Markdown 图片展示。

## 各栏目当前规则

### 学习

- 秋招面试经历：可记录年份、目标方向、流程阶段、题目类型、复盘和建议。
- 人工智能智能体学习：可记录概念、工具或模型、资料来源、实践结果和适用版本。
- LeetCode 解题：可记录题号、题名、难度、使用语言、核心思路、时间复杂度、空间
  复杂度和代码。
- 学习内容主要自留自用，因此不强制每篇都写面向新读者的完整背景介绍。
- 面试内容默认匿名化，不公开可识别公司、面试官、个人或未公开流程的信息；不得发布
  受保密要求约束的题目原文。以后确需公开具体名称时，应逐篇确认。

### 游戏

- Celeste 每张地图对应一篇详细游玩评价。地图名使用文章标题，简评使用摘要，总体评分
  使用十分制浮点 `rating`；地图所在合集、难度和主要 gameplay 使用专用字段。难度和
  gameplay 是作者手动填写的普通文本，不建立标签词表。
- 三个专用字段分别是 `celesteCollection`、`celesteDifficulty` 和 `celesteGameplay`。
  合集字段只保存稳定编号；合集显示名称和颜色统一保存在
  `src/data/celeste-collections.json`，该文件同时供 Front Matter CMS 和公开页面读取。
- `celesteVideoUrl` 是 Celeste 地图文章的可选 Bilibili 游玩视频网址。它与地图汇总表的
  结构化比较字段分开维护，只在文章元数据/封面之后、正文之前显示“游玩视频”入口；未
  填写时不显示空占位。该字段只允许出现在 Celeste 地图文章中，其他文章填写会被内容
  校验拒绝。
- Celeste 合集使用集中注册表，统一维护显示名称和颜色；文章只选择合集，不逐篇保存
  颜色。同一合集在筛选、桌面表格和手机卡片中使用一致标记；颜色始终与文字同时出现，
  “独立地图”使用中性灰色。
- Celeste 汇总页位于 `/posts/games/celeste/`，从公开单篇文章元数据自动生成，避免在
  文章和表格中重复维护数据。桌面显示语义表格，手机显示相同信息的纵向卡片；地图名
  直接链接详细文章。
- 汇总页支持全文搜索、合集筛选，以及地图名和评分排序。全文搜索覆盖地图名、合集、
  难度、主要 gameplay 和简评；默认按评分从高到低排列，同分按地图名排列。难度与
  gameplay 只参与文本搜索，不作为固定筛选项。
- Minecraft 单篇记录：游戏版本、模组加载器、模组或整合包名称与版本、游玩阶段和
  体验评价。
- 其他 Steam 游戏：游戏名、游玩状态、日期、评价和相关文章。
- 客观或社区常用难度、个人评分、个人推荐度和定性推荐档位必须分开，不能互相替代。
- 包含关键剧情、地图机制解法或其他可能影响初见体验的内容时，使用剧透字段并在正文
  前给出提醒。

### WOTA艺

- 保持三个并列入口：我的作品、我喜欢的作品、副歌技汇总。
- WOTA艺文章必须通过 `wotaSection` 明确归入上述三类之一；构建检查会阻止漏填或在其他
  栏目误填该字段，避免文章被放入不确定位置。
- 字段取值固定为：`my-works` 对应“我的作品”，`favorite-works` 对应“我喜欢的作品”，
  `chorus-techniques` 对应“副歌技汇总”。标签显示中文，字段值使用稳定英文，避免以后
  修改显示文案时破坏文章数据。
- 三类上方预留一段栏目级固定总结文字。它不是博客文章，不参与标签、归档、RSS 或搜索
  结果；当前保持空白，用户以后提供内容后再公开显示，不发布模板占位文案。
- 企划和技连作为 WOTA艺作品的呈现形式，用于描述“我的作品”或“我喜欢的作品”，
  不额外提升为全站主分类。
- 副歌技是 WOTA艺的基础组成部分；汇总条目以后可以关联采用该副歌技的作品。
- 我的作品可记录发布时间、参与者、使用曲目、作品形式、相关技和外部作品链接。
- 我喜欢的作品可记录作品来源、作者或企划、喜欢的原因、作品形式和关联技。
- 外部作品必须保留作者或发布者、原始链接和必要署名，不默认转载完整媒体文件。
- 公开博客不专门解释 WOTA艺、企划、技连和副歌技；目标读者按已了解这些概念设计。

### 动漫

- 一条记录对应一个季度、剧场版或独立作品；单集感想放在对应记录内部，不默认创建
  单集级页面。
- 可记录作品名、季度或年份、观看状态、观看日期、感受、评价和剧透标记。
- 汇总页从单篇记录读取观看状态、评分和推荐度，不手工复制相同数据。
- 涉及剧情信息时使用剧透字段，并在列表或正文入口处提醒读者。

## 导航与查找

采用较小的全站导航：`首页`、`文章`、`关于`，并保留搜索入口。在“文章”页和首页
显著展示 `学习`、`游戏`、`WOTA艺`、`动漫` 四个栏目入口。这样可以加强扩展性，未来
增加子主题时不需要持续扩张顶部导航。

每个栏目页负责：

- 显示栏目说明、最新文章和稳定子主题。
- 提供相关汇总页，例如 Celeste 地图汇总。
- 允许通过主题标签、内容类型和发布时间继续细分，并显示每个入口包含的文章数量。
- 为从搜索或外部链接进入的读者显示当前位置和返回栏目入口。

游戏栏目的“主题标签”是按游戏进入专属内容区的导航，只从文章的 `subcategory` 生成
`Celeste`、`Minecraft` 等游戏名，不遍历文章的普通 `tags`。普通标签仍可用于描述
“整合包”“科技包”等内容，但不混入游戏导航。点击 Celeste 直接进入地图汇总页；
`/posts/games/` 的栏目文章顶部固定显示地图汇总入口，单张地图文章仍按正常文章继续
列在入口之后。

栏目内浏览状态使用静态网址保存，例如
`/posts/learning/tags/<标签>/`、`/posts/learning/types/note/` 和
`/posts/learning/archive/2025/`。这样链接不依赖浏览器脚本，可以被收藏、复制和搜索
引擎理解；标签和年份入口只在确实存在文章时生成，避免显示大量空选项。第一阶段按年份
提供时间入口，等文章数量需要时再增加月份，避免为当前少量内容引入过细层级。

文章正文与栏目浏览使用不同宽度：正文继续保持约 48rem 的阅读行长，栏目页在宽屏使用
较宽的页面框架和“浏览入口 + 文章结果”双栏结构；中小屏按相同阅读顺序堆叠为单栏。
响应式布局以内容是否拥挤或过疏为断点依据，不按具体设备型号硬编码。

现有 Pagefind 搜索继续覆盖全部公开文章。Pagefind 是构建网站时生成的静态全文搜索
工具，不需要数据库。内容量较少时不增加复杂筛选；文章明显增多后，再考虑按主分类、
游戏或内容类型过滤。

## 网址规则

界面标签使用中文，网址采用稳定的英文小写路径，例如：

- `/posts/learning/...`
- `/posts/games/celeste/...`
- `/posts/games/minecraft/...`
- `/posts/wota/...`
- `/posts/anime/...`

迁移时不保留旧文章网址，也不为旧网址增加重定向。这样实现和维护最简单，但已有书签、
搜索结果或外部引用会失效；用户已接受这一影响。具体迁移仍属于后续开发任务，本轮不
修改任何文章路径。

## 已确认的当前方案

- IA-001 受众：学习内容以自用为主；游戏、WOTA艺和动漫以公开分享为主。
- IA-002 导航：使用小型全站导航，四个内容栏目通过首页和文章页进入。
- IA-003 归属：每篇文章一个主分类，允许多个标签。
- IA-004 网址：页面显示中文，网址使用英文小写路径，不保留旧网址。
- IA-005 WOTA艺：不做公开术语解释；三个内容入口并列且每篇文章必须明确归属，作品
  形式和基础技通过字段及关联表达；顶部总结使用独立固定文字并在用户填写前保持隐藏。
- IA-007 安全：面试内容默认匿名化；游戏和动漫采用文章级剧透标记与阅读前提醒。
- IA-008 动漫粒度：按季度、剧场版或独立作品建记录，单集内容收在记录内部。

这些决定是当前可实施基线，不妨碍后续按实际前端效果调整。

## 已确认的评价规则

### IA-006：评分、推荐度与定性档位

同时保留以下三种个人评价，而且评分与推荐度不是同一个概念：

1. 评分是作者对作品或体验本身综合质量的个人评价，采用十分制并允许小数。
2. 推荐度是作者愿意向目标读者推荐它的程度，采用十分制并允许小数；它会考虑受众
   匹配、入门门槛等因素，所以可能与评分不同。
3. 定性推荐档位从推荐度自动换算，避免文字档位与数值互相矛盾。

定性档位的具体名称和数值阈值在设计游戏或动漫汇总页时结合实际版面确认。该细节只
影响显示文案和换算函数，不改变文章需要保存的评分与推荐度数据，因此不阻塞栏目开发。

## 当前实现边界

- 已建立四个栏目页、栏目入口、空状态、统一文章元数据接口和展示组件。
- 栏目页已把正文阅读宽度和浏览宽度分开，并提供栏目内标签、内容类型和年份入口；
